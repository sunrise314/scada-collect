# 万级点位元数据管理

## 一、回顾与本章问题

上一章我把 4 个 Driver 讲透了——Modbus 批量合并、OPC UA 订阅兜底、S7 走 PLC4X、MQTT 走 Paho 订阅。但 Driver 只是"执行者"，它要读什么、怎么算工程量、多久读一次、哪些变化才推送，这些"业务规则"全都靠点位元数据驱动。

这一章讲的是 SCADA 系统里最不起眼却最关键的一块：点位表。一个 4-16 台 PLC 的中型工厂，点位轻松过万。这 1 万行元数据怎么建模、怎么校验、怎么让 Driver 用得舒服，决定了整个系统是不是"能商用"。

## 二、行业对比：点位模型怎么设计

ThingsBoard 的设备模型走"共享设备配置"（Device Profile）+ 遥测键值对（telemetry key-value）。优点是动态——设备上线自己声明有哪些 key。缺点是工业现场不买账：PLC 里的寄存器地址是固定的，你让 PLC"自己声明"它有 HR40001 这个温度点位，PLC 做不到。所以 ThingsBoard 接 Modbus 要靠 Integration 转换，把"寄存器地址"翻译成"遥测 key"，中间多一层映射。

Ignition 的点位叫 Tag，分 OPC Tag、Device Tag、UDT（用户定义类型）。它的 UDT 是工业现场的神器——你定义一个"电机"UDT 包含转速/电流/温度/状态 4 个 tag，实例化 100 台电机就是 100 个 UDT 实例，改 UDT 全量生效。这是商用 SCADA 的成熟度体现。

我的取舍是介于两者之间的"平表 + 强类型字段"模型。不上 UDT 抽象（中小工厂点位规模 1 万内，没必要那么重），也不学 ThingsBoard 的动态 key-value（失去类型安全，时序库列类型没法推导）。直接用一张关系表，每个点位一行，字段类型严格定义。简单粗暴，但够用。

## 三、点位实体：ScadaPointDO

核心实体在 `yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/dal/dataobject/point/ScadaPointDO.java`。一台设备典型有 100-5000 个点位，超过 5000 我建议拆子设备。关键字段：

```java
@TableName("scada_point")
@Data
@SuperBuilder
public class ScadaPointDO extends BaseDO {
    @TableId(type = IdType.AUTO)
    private Long id;

    private Long deviceId;
    /** 点位标签，用作 TDengine 子表名，禁止含中文，建议 [a-z][a-z0-9_]{2,63} */
    private String tag;
    private String name;
    /** 协议地址，格式因 protocolType 而异 */
    private String address;
    private Integer pointType;
    private String engUnit;
    @Builder.Default private BigDecimal scale = BigDecimal.ONE;
    @Builder.Default private BigDecimal offset = BigDecimal.ZERO;
    private BigDecimal minVal;
    private BigDecimal maxVal;
    @Builder.Default private BigDecimal deadBand = BigDecimal.ZERO;
    @Builder.Default private Integer scanRateMs = 1000;
    @Builder.Default private String rwFlag = "R";
    @Builder.Default private Boolean enabled = true;
}
```

几个字段的取舍要展开讲。

**`tag` 为什么租户内唯一不是全局唯一？** yudao 的多租户拦截器给所有查询注入 `tenant_id` 条件，同一个 tag 只可能属于一个租户。让 tag 全局唯一反而难处理——租户 A 用了 `temp_1`，租户 B 想用同名就得改名。DDL 的唯一索引是 `uk_tenant_tag (tenant_id, tag, deleted)`，租户内唯一足够。而且 tag 直接用作 TDengine 子表名，TDengine 子表名是全局命名空间，但 scada-collect 是单租户单实例部署，子表名冲突不会发生。

**`tag` 为什么禁止含中文？** TDengine 子表名不支持中文字符（实际是兼容性问题，中文子表名在部分客户端工具里会乱码）。DDL 注释里建议 `[a-z][a-z0-9_]{2,63}`，但代码层没做强校验——这是个 TODO，商用版应在 `ScadaPointServiceImpl.createPoint` 加正则校验。

**`scale` / `offset` 怎么用？** 工程量转换公式 `eng = raw * scale + offset`。典型场景：4-20mA 传感器，PLC 寄存器存的是 0-27648（西门子标准模拟量），要转成 0-100℃ 的工程量，scale = 100/27648，offset = 0。代码在 ModbusTcpDriver 的 `scaleValue`：

```java
private BigDecimal scaleValue(ScadaPointDO point, int raw) {
    if (point.getPointType().equals(ScadaPointType.BOOL.getType())) {
        return BigDecimal.valueOf(raw != 0 ? 1 : 0);
    }
    double scaled = raw * point.getScale().doubleValue() + point.getOffset().doubleValue();
    if (point.getMinVal() != null && scaled < point.getMinVal().doubleValue()) {
        scaled = point.getMinVal().doubleValue();
    }
    if (point.getMaxVal() != null && scaled > point.getMaxVal().doubleValue()) {
        scaled = point.getMaxVal().doubleValue();
    }
    return BigDecimal.valueOf(scaled);
}
```

注意量程截断——传感器坏值可能让 raw 跳到 65535，不截断会算出离谱的工程量。设计意图是：工程量转换在 Driver 层就完成，不要把原始寄存器值塞进时序库再查询时算，否则每次查询都要走 CAST 重算。

**`deadBand` 死区怎么算？** 它是百分比 0-100，0 表示任何变化都推送。比如某温度点位量程 0-100℃，deadBand=2，那变化超过 2℃ 才推送一次。这是为了抑制传感器末位抖动——温度传感器末位 ±0.1℃ 抖动是常态，不设死区 1Hz 全量推 SSE，前端会被噪声刷花。死区比较的伪代码：`abs(new - last) / (max - min) * 100 >= deadBand` 才推送。商用版应把这个判断放在 `RealtimePushService.submit` 里做，Driver 层不管。

**`scanRateMs` 为什么建议 ≥ 1000？** 1Hz（1000ms）是商用 SCADA 的甜点。再快有两个问题：一是 PLC 侧的 Modbus 从站响应有 50-200ms 延迟，scanRate=100ms 时 10 个点位就吃满 1 秒；二是万级点位 100ms 采集 = 10w points/s 写入，TDengine 单节点虽能扛但磁盘和网络吃不消。除非关键参数（比如注塑压力要 100ms），否则 1Hz 足够。

**`rwFlag` R/W/RW** 控制反控权限。R 只读不能写，W 只写不采集（用于纯反控点位），RW 读写。Driver 的 `writeOne` 实现里应校验 rwFlag，但当前代码省略了这层校验——这是个已知 TODO。

## 四、点位类型枚举：ScadaPointType

点位类型决定 TDengine 子表列类型推导，代码在 `enums/ScadaPointType.java`：

```java
public enum ScadaPointType implements IntArrayValuable {
    BOOL(1, "开关量"),
    INT(2, "整型"),
    FLOAT(3, "浮点"),
    STR(4, "字符串");
}
```

TDengine 列类型按此推导：BOOL→BOOL，INT→BIGINT，FLOAT→DOUBLE，STR→NCHAR(64)。注意 FLOAT 的 scale/offset 在 Driver 层就完成转换，时序库存的是工程量不是原始寄存器值。枚举注释里我特意写了这句话，因为这是新人最容易踩的坑——把原始寄存器值塞时序库，查询时再算工程量，性能爆炸。

## 五、Mapper 与 N+1 防范

点位查询是采集执行器最高频的路径，必须避免 N+1。代码在 `dal/mysql/point/ScadaPointMapper.java`：

```java
@Mapper
public interface ScadaPointMapper extends BaseMapperX<ScadaPointDO> {

    default List<ScadaPointDO> selectListByDevice(Long deviceId) {
        return selectList(new LambdaQueryWrapperX<ScadaPointDO>()
                .eq(ScadaPointDO::getDeviceId, deviceId)
                .eq(ScadaPointDO::getEnabled, true));
    }

    default List<ScadaPointDO> selectListByIds(Collection<Long> ids) {
        return selectList(new LambdaQueryWrapperX<ScadaPointDO>()
                .in(ScadaPointDO::getId, ids));
    }

    default ScadaPointDO selectByTag(String tag) {
        return selectOne(new LambdaQueryWrapperX<ScadaPointDO>()
                .eq(ScadaPointDO::getTag, tag));
    }
}
```

`selectListByIds` 是采集任务执行时的关键查询——任务里存的是 `pointIdsJson`（点位 ID 数组），执行时一次批量加载所有点位。如果改成逐个 `selectById`，100 个点位 100 次 SQL，1Hz 扫表会被 SQL 拖死。`in` 查询走主键索引，毫秒级返回。设计意图是：高频路径的查询要么走索引、要么走缓存，绝不走 N+1。

## 六、服务层与 Controller

服务层 `service/point/ScadaPointServiceImpl.java` 比较薄，核心是 tag 唯一性校验：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public Long createPoint(ScadaPointSaveReqVO reqVO) {
    if (reqVO.getTag() != null && pointMapper.selectByTag(reqVO.getTag()) != null) {
        throw new RuntimeException("tag 已存在: " + reqVO.getTag());
    }
    ScadaPointDO point = new ScadaPointDO();
    BeanUtils.copyProperties(reqVO, point);
    pointMapper.insert(point);
    return point.getId();
}
```

这里有个并发隐患——两个请求同时建同名 tag，校验都能通过，最后唯一索引兜底抛 `DuplicateKeyException`。商用版应 catch 这个异常转成业务错误码，而不是让 `RuntimeException` 冒泡。当前实现是 MVP 版本，唯一索引是最后防线，代码层校验是用户体验优化。

Controller 在 `controller/admin/point/ScadaPointController.java`，标准的 RESTful CRUD + 一个 `list-by-device`：

```java
@GetMapping("/list-by-device")
@Operation(summary = "按设备列出点位")
public CommonResult<List<ScadaPointRespReqVO>> listByDevice(@RequestParam("deviceId") Long deviceId) {
    List<ScadaPointDO> list = pointService.listByDevice(deviceId);
    return success(list.stream().map(this::convert).toList());
}
```

`list-by-device` 是给配置页面用的——选了某台设备后，前端要拉这台设备的所有点位做勾选。这个接口走 `selectListByDevice` 走 `idx_device` 索引，1000 个点位毫秒返回。

请求 VO `ScadaPointSaveReqVO` 用了 Bean Validation：

```java
@NotNull(message = "设备 ID 不能为空")
private Long deviceId;
@NotEmpty(message = "点位标签不能为空")
private String tag;
@NotNull(message = "点位类型不能为空")
private Integer pointType;
```

`@NotEmpty` 用在 String 上，既校验 null 又校验空串。`@NotNull` 用在 Long/Integer 上只校验 null。这是 Bean Validation 的基本用法，但很多团队图省事全用 `@NotNull`，String 空串就漏过去了。

## 七、设备表为什么用 JSON 存连接参数

点位挂在设备下，设备表 `dal/dataobject/device/ScadaDeviceDO.java` 有个关键字段 `conn_params_json`：

```java
/** 连接参数 JSON，见类注释 */
private String connParamsJson;
```

为什么不用一张子表存连接参数？因为不同协议字段差异极大：Modbus 是 `{host, port, slaveId}`、OPC UA 是 `{endpointUrl, securityPolicy, username, password}`、S7 是 `{host, rack, slot}`、MQTT 是 `{brokerUrl, group, edgeNode, clientId}`。

如果做子表，要么字段稀疏（一行存一个 key-value，4 种协议撑出 20 列空字段），要么做 EAV 模型（key-value 横表，查询要 self-join 性能爆炸）。JSON 字段 + Driver 层强校验是最务实的方案——存的时候灵活，读的时候由 Driver 反序列化成自己要的结构，字段缺失在 Driver 层报错。

代价是没法用 SQL 直接查"所有 slaveId=1 的设备"。但这个查询需求几乎不存在——设备管理按 code 查、按 protocol_type 筛，不需要按连接参数字段筛。如果真有需求，MySQL 8.x 的 JSON_EXTRACT 函数能搞定，性能也不差。

## 八、调优与踩坑

一是**点位批量导入**。1 万个点位用单条 `create` 接口录完得半天。商用版应加 Excel 导入接口，走 MyBatis-Plus 的 `saveBatch`，但要注意 tag 唯一性校验在批量场景下要改成"先查所有 tag 一次、内存里去重"，不能每行都 `selectByTag`。

二是**tag 改名导致 TDengine 子表名变更**。tag 用作子表名，一旦点位创建并写入了数据，改 tag 等于换子表名，历史数据会"断档"。商用版应在 `updatePoint` 里检测 tag 变更，要么禁止改、要么做 ALTER TABLE RENAME。当前代码没处理这个，是已知缺陷。

三是**scale/offset 的精度**。DDL 里 scale/offset 用 `DECIMAL(18,6)`，6 位小数对绝大多数工业场景够，但精密仪器可能要 8 位。生产环境遇到精度不足再调 DDL。

四是**scanRateMs 不能小于设备响应时间**。某客户把所有点位设成 100ms，结果 Modbus 一台设备 200 个点位，扫一轮要 4 秒（200 个寄存器 × 20ms 响应），100ms 任务永远到不了下一轮。最后把高频点位单独拆一个任务，低频点位 1Hz 一个任务，才解决。

## 九、商用化检查清单

- tag 命名规则有正则校验吗？禁止中文、禁止特殊字符、长度限制。
- tag 改名或删除后历史数据怎么办？TDengine 子表是否保留？
- 死区判断在 Driver 层还是推送层？建议推送层，Driver 层只管读。
- 点位批量导入支持吗？Excel/CSV 都要支持，导入前预校验 tag 重复。
- 设备连接参数 JSON 字段有版本兼容吗？协议升级加字段时老数据怎么迁移？
- 反控权限 rwFlag 有没有在 writeOne 里校验？这是安全审计的硬要求。
- 点位启用/禁用后采集任务有没有动态刷新？当前实现是任务重启才生效，商用版应支持热更新。

到这里，点位元数据的"是什么"讲完了。但"什么时候读、谁去读、读到坏值怎么办"是下一章的重头戏——1Hz 扫表会不会漏？指数退避为什么 30 秒封顶？TDengine 挂了的数据往哪补？采集任务调度与断线重连是整个系统最考验工程功底的一块。
