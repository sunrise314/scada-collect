# 采集任务调度与断线重连

## 一、回顾与本章问题

前三章走下来，骨架立住了：第一章讲清 5 张表领域模型，第二章讲透 4 个 Driver 怎么连怎么读，第三章讲点位元数据怎么建模怎么校验。但有个问题一直没碰——谁去触发 Driver 读？什么时候读？读到一半 PLC 掉线了怎么办？TDengine 临时挂了，这一秒的数据往哪放？

这一章回答的就是这几个"运行时"的问题。它是整个 SCADA 系统最考验工程功底的一块，因为这里全是并发、状态机、容错，写错一处就是数据丢失或雪崩重连。

## 二、行业对比：调度模型怎么选

Quartz 是 Java 圈最出名的调度框架，yudao 自己也集成了。它的优势是 cron 表达式灵活、支持持久化、集群部署不重复执行。但 SCADA 不需要"每天 9 点跑"这种 cron 语义，要的是"每 1 秒跑一次"的固定周期。Quartz 的 trigger 表加锁机制在 1Hz 高频调度下会成为瓶颈——每次触发都要 SELECT FOR UPDATE 锁 QRTZ_LOCKS 表，几百个任务秒级触发，锁竞争严重。

ThingsBoard 的调度走 Actor 模型，每个设备一个 Actor，消息驱动。优雅但重——Akka Toolkit 一上来，部署、调试、监控全要跟着 Actor 体系走。中小工厂不需要这种复杂度。

Ignition 的调度是内置的，叫 Tag Group，按扫描模式（Driven/Direct/Leased）分类，工业级但闭源。

我的取舍是"自己写 ScheduledExecutor + 扫表"，单线程扫表 + 多线程执行。代码在 `yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/service/collect/CollectTaskExecutor.java`。轻量、可控、不依赖额外框架。

## 三、调度模型：单线程扫表 + 线程池执行

核心调度就一个 `ScheduledExecutorService`，每 1 秒扫一次：

```java
private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor(
        r -> { Thread t = new Thread(r, "scada-sched"); t.setDaemon(true); return t; });

public void start() {
    scheduler.scheduleAtFixedRate(this::scanAndExecute, 5, 1, TimeUnit.SECONDS);
}
```

`initialDelay=5` 秒是为了等容器完全启动、连接池暖起来。`scheduleAtFixedRate` 是固定频率（不是固定间隔），如果上一轮执行超时，下一轮会立即补上不累计延迟——这对 1Hz 采集是正确语义。

**1Hz 扫表会不会漏？** 不会，但有前提。`scanAndExecute` 里判断任务是否到点的逻辑：

```java
private boolean isDue(ScadaCollectTaskDO task, LocalDateTime now) {
    if (task.getLastRunAt() == null) return true;
    long nextRunAtMs = task.getLastRunAt()
            .atZone(ZoneId.systemDefault()).toInstant().toEpochMilli()
            + (task.getIntervalMs() == null ? 1000 : task.getIntervalMs());
    long nowMs = now.atZone(ZoneId.systemDefault()).toInstant().toEpochMilli();
    return nowMs >= nextRunAtMs;
}
```

`isDue` 用 `lastRunAt + intervalMs <= now` 判断，不是用"当前秒是不是 intervalMs 的整数倍"。这意味着如果某轮任务执行了 1.5 秒（超时），下一秒扫表时 `now - lastRunAt = 1.5s >= 1s`，任务立即被标记为 due 再次执行——不会因为上一轮超时就跳过这一轮。这是"补跑"语义，不是"漏跑"语义。真正会漏的极端情况是单线程扫表本身被某轮 execute 阻塞超过 1 秒，但 `scanAndExecute` 里所有任务提交都是 `executor.submit`（异步），不会阻塞扫表线程，所以扫表本身是秒级的。

线程池配置：

```java
private void initExecutor() {
    this.executor = new ThreadPoolExecutor(
            8, 32, 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(200),
            r -> { Thread t = new Thread(r, "scada-exec"); t.setDaemon(true); return t; },
            new ThreadPoolExecutor.CallerRunsPolicy());
}
```

**为什么用 `CallerRunsPolicy` 不用 `AbortPolicy`？** AbortPolicy 队列满直接抛异常，任务丢了——SCADA 数据丢一秒就是事故。CallerRunsPolicy 队列满后让调用方（也就是扫表线程 scada-sched）自己跑这个任务，自然形成背压：扫表线程被占住，下一秒扫表就延迟，整个系统负载自动降下来，不丢任务。这是 IO 密集型任务线程池的标准做法。

in-flight 防重是另一个关键：

```java
if (runningTaskIds.containsKey(task.getId())) continue;
runningTaskIds.put(task.getId(), true);
executor.submit(() -> {
    try {
        executeTask(task);
    } finally {
        taskMapper.updateRunStat(task.getId(), LocalDateTime.now(), dur, error);
        runningTaskIds.remove(task.getId());
    }
});
```

`runningTaskIds` 是 `ConcurrentHashMap<Long, Boolean>`，标记正在执行的任务。上一轮没跑完的下一轮不重复提交——因为 Modbus 一台设备一个连接（第二章讲的 maxTotalPerKey=1），重复提交会阻塞在 borrowObject 上白白占线程。设计意图是：同一任务的串行性靠应用层 in-flight 集合保证，不靠数据库锁。

## 四、任务执行流程

`executeTask` 是单任务执行的完整链路：

```java
private void executeTask(ScadaCollectTaskDO task) {
    ScadaDeviceDO device = connectionManager.getOrConnect(task.getDeviceId());
    if (device == null) throw new RuntimeException("设备不可用");
    List<Long> pointIds = parsePointIds(task.getPointIdsJson());
    List<ScadaPointDO> points = pointMapper.selectListByIds(pointIds);
    List<PointValue> values = driverManager.readBatch(device, points);
    List<PointValue> goodValues = values.stream().filter(PointValue::isGood).collect(Collectors.toList());
    if (goodValues.isEmpty()) return;
    try {
        valueService.writeBatch(goodValues);
    } catch (Exception e) {
        log.warn("TDengine 写入失败，进入补采队列: {}", e.getMessage());
    }
    try { pushService.submit(goodValues); } catch (Exception ignored) {}
    try { alarmEngine.onValues(goodValues); } catch (Exception ignored) {}
    connectionManager.onHeartbeat(device.getId());
}
```

七步：设备就绪校验 → 批量加载点位 → Driver 读 → 过滤坏值 → 写 TDengine → 推 SSE → 进告警引擎 → 更新心跳。每一步用 try-catch 兜底，下游失败不影响上游——SSE 挂了告警还要跑，告警挂了数据还要写。这是"管道隔离"原则，工业 SCADA 不能因为一个组件挂了全链路雪崩。

`selectListByIds` 是第三章讲的 N+1 防范，1000 个点位一条 SQL 拿完。`pointIdsJson` 存 JSON 数组避免关联表 N+N 查询，这是 DDL 设计时就定好的。

任务表 `dal/dataobject/task/ScadaCollectTaskDO.java` 的 `task_type` 分 POLL/SUBSCRIBE：POLL 是轮询按 intervalMs 周期读，SUBSCRIBE 仅 OPC UA 支持由设备推送。`concurrent` 默认 false 避免乱序——同一任务前一轮没跑完，下一轮不能并发，否则 Modbus 报文会交错。

任务统计回写用 `@Update` 注解而不是 `updateById`：

```java
@Update("UPDATE scada_collect_task SET last_run_at = #{runAt}, last_duration_ms = #{durMs}, " +
        "last_error = #{error}, run_count = run_count + 1, " +
        "error_count = error_count + CASE WHEN #{error} IS NULL THEN 0 ELSE 1 END " +
        "WHERE id = #{id} AND deleted = 0")
int updateRunStat(@Param("id") Long id, @Param("runAt") LocalDateTime runAt,
                  @Param("durMs") Long durMs, @Param("error") String error);
```

为什么不用 `updateById`？yudao 的 BaseDO 带乐观锁版本号，`updateById` 会带 `version = version + 1 WHERE version = #{version}`。1Hz 高频更新同一行，乐观锁冲突概率很高，重试反而拖慢。用 `@Update` 走原子自增（`run_count = run_count + 1`），无锁，永远成功。

## 五、断线重连状态机

设备状态管理在 `service/collect/DeviceConnectionManager.java`，状态机 6 态：DISABLED/UNKNOWN/CONNECTING/CONNECTED/RECONNECTING/ERROR。`getOrConnect` 是入口：

```java
public ScadaDeviceDO getOrConnect(Long deviceId) {
    ScadaDeviceDO device = deviceCache.computeIfAbsent(deviceId, this::loadDevice);
    if (device == null) return null;
    if (Boolean.FALSE.equals(device.getEnabled())) return null;
    Integer status = device.getStatus();
    if (status == null) status = ScadaDeviceStatus.UNKNOWN.getState();
    if (status.equals(ScadaDeviceStatus.DISABLED.getState())) return null;
    if (status.equals(ScadaDeviceStatus.ERROR.getState())) return null;
    if (status.equals(ScadaDeviceStatus.RECONNECTING.getState())) {
        tryReconnect(device);
        return null;
    }
    return device;
}
```

DISABLED/ERROR 直接拒绝（返回 null 让任务挂起），RECONNECTING 触发一次重连尝试但不阻塞当前任务（返回 null）。设计意图是：状态判定不阻塞调用方，重连是异步的，当前秒数据丢了就丢了，下一秒重连成功再继续。

**指数退避为什么 30 秒封顶？** 重连退避算法：

```java
private long computeBackoffMs(int attempt) {
    long base = 1000L * (1L << Math.min(attempt, 5));
    return Math.min(base, 30_000);
}
```

1/2/4/8/16/30/30...秒。前 5 次指数增长（1→2→4→8→16），第 6 次起封顶 30 秒。为什么 30 秒？太短（比如 5 秒封顶）会让掉线的 PLC 被疯狂重连，PLC 侧连接配额可能被打满；太长（比如 5 分钟封顶）工厂网络恢复后要等太久。30 秒是经验值——工厂局域网抖动一般 30 秒内恢复，超过 30 秒多半是物理故障，人工介入比盲目重连有效。重连守护线程 500ms 扫一次：

```java
private void startReconnectDaemon() {
    Thread t = new Thread(() -> {
        while (!Thread.currentThread().isInterrupted()) {
            for (Map.Entry<Long, ReconnectState> e : reconnectStates.entrySet()) {
                if (now < s.nextAttemptAt) continue;
                tryReconnect(device);
            }
            Thread.sleep(500);
        }
    }, "scada-reconnect");
}
```

500ms 扫一次是因为退避最小 1 秒，扫得比退避细 2 倍足够精确，不会让重连延迟超过 500ms。

心跳守护 60 秒扫一次，cutoff 30 秒：

```java
private void startHeartbeatWatchdog() {
    Thread t = new Thread(() -> {
        while (!Thread.currentThread().isInterrupted()) {
            Thread.sleep(60_000);
            LocalDateTime cutoff = LocalDateTime.now().minusSeconds(30);
            for (ScadaDeviceDO d : deviceCache.values()) {
                if (d.getLastHeartbeatAt() == null || d.getLastHeartbeatAt().isBefore(cutoff)) {
                    onConnectionError(d.getId(), "心跳超时 30s");
                }
            }
        }
    }, "scada-heartbeat");
}
```

心跳超时 30 秒就转 RECONNECTING。为什么 30 秒？正常 1Hz 采集每秒都有心跳，30 秒没心跳说明要么 PLC 死了要么网络断了。短于 30 秒容易误判（比如某轮采集卡 5 秒），长于 30 秒故障发现太晚。

## 六、补采队列：RocksDB

TDengine 临时挂了，这一秒的数据不能丢。代码在 `service/collect/ReplayBuffer.java`，基于 RocksDB：

```java
public ReplayBuffer(@Value("${scada.replay.path:./data/scada-replay}") String path,
                    @Value("${scada.replay.max-keys:1000000}") long maxKeys) {
    Options opts = new Options().setCreateIfMissing(true);
    this.db = RocksDB.open(opts, dir.getAbsolutePath());
}
```

**为什么用 RocksDB 不直接用内存队列？** 三个理由：一是磁盘持久，进程重启不丢，符合 SCADA 数据完整性要求；二是嵌入式不需要外部依赖（不依赖 Redis），简化部署；三是天然 key 排序——以 timestamp+pointId 为 key，回放时按序读出。内存队列（比如 LinkedBlockingQueue）重启就丢，而且容量受 JVM 堆限制，万级点位补采 1 小时就是 3600w 条，内存扛不住。

key 设计是关键：

```java
private byte[] makeKey(PointValue v) {
    long ts = v.ts().atZone(ZoneId.systemDefault()).toInstant().toEpochMilli();
    byte[] b = new byte[16];
    for (int i = 7; i >= 0; i--) b[7 - i] = (byte) ((ts >>> (8 * i)) & 0xFF);
    long pid = v.pointId() == null ? 0 : v.pointId();
    for (int i = 7; i >= 0; i--) b[15 - i] = (byte) ((pid >>> (8 * i)) & 0xFF);
    return b;
}
```

13 位时间戳（实际用 8 字节存毫秒）+ 8 字节 pointId，共 16 字节，大端序。大端序让 RocksDB 的 LSM 排序天然按时间升序，回放时 `seekToFirst` 顺序读就是时间序。容量保护 `maxKeys=100w` 默认（约 1 小时补采量），超容淘汰最老的——这个淘汰逻辑当前是简化版，商用版应实现迭代删除最老 10%。

回放是 drain 语义：

```java
public List<PointValue> drain(int batchSize) {
    try (var iter = db.newIterator()) {
        iter.seekToFirst();
        while (iter.isValid() && n < batchSize) {
            out.add(decodeValue(iter.value()));
            db.delete(iter.key());
            iter.next();
        }
    }
    return out;
}
```

读一条删一条，保证不重复回放。商用版应在 TDengine 恢复后由独立线程持续 drain，限速回放避免冲击 TDengine 写入。

## 七、启动与装配

调度入口在 `job/ScadaCollectJob.java`，用 `ApplicationRunner` 而不是 `@PostConstruct`：

```java
@Component
public class ScadaCollectJob implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        if (!scadaConfig.isCollectEnabled()) {
            log.info("SCADA 调度未启用（scada.collect.enabled=false）");
            return;
        }
        executor.start();
    }
}
```

`ApplicationRunner` 在所有 Bean 初始化完、连接池暖起来后才执行，避免高频读冲击还没准备好的连接池。`scada.collect.enabled` 开关让开发环境能关闭采集（开发时不连真实 PLC）。

线程池 bean 在 `framework/scada/config/ScadaConfiguration.java`：

```java
@Bean(name = "scadaCollectExecutor")
public ThreadPoolExecutor scadaCollectExecutor(ScadaProperties props) {
    return new ThreadPoolExecutor(
            tp.getCoreSize(), tp.getMaxSize(), 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(tp.getQueueSize()),
            r -> { Thread t = new Thread(r); t.setName("scada-collect-" + t.getId()); t.setDaemon(true); return t; },
            new ThreadPoolExecutor.CallerRunsPolicy());
}
```

**为什么独立池不用 yudao 全局池？** SCADA 的 IO 任务是阻塞型（等 PLC 响应、等 TDengine 写），跟 yudao 默认池里 CPU 密集型任务（Excel 导出、邮件发送）放一起会互相拖慢。独立池便于按业务限流，jstack 时 `scada-collect-` 前缀一眼能找到。配置走 `scada.thread-pool.core-size/max-size/queue-size`，生产可调。

## 八、调优与踩坑

一是**1Hz 扫表的 SQL 要走索引**。`selectEnabledTasks` 查 `enabled=true`，必须走 `idx_enabled_due (enabled, last_run_at)` 索引。任务表几十到几百行，走索引毫秒级，全表扫也才几毫秒，但任务表涨到几千行时差距就出来了。

二是**线程池队列不能设太大**。队列 200 看着小，但配合 CallerRunsPolicy 是对的——队列太大（比如 10000）会让任务堆积在内存里，OOM 风险，而且堆积的任务 lastRunAt 已经过时，执行完写入的也是过期数据。200 + CallerRuns 让背压立即传导。

三是**心跳更新不能每秒写 DB**。`onHeartbeat` 里只在状态变化时写 DB，正常 CONNECTED 状态每秒心跳只更新内存不写库，否则 1Hz × 100 台设备 = 100 次/秒 UPDATE，MySQL 写入压力大。

四是**ReplayBuffer 路径要配独立磁盘**。RocksDB 写入是顺序写，放系统盘会和 OS 争 IO。生产环境建议挂载数据盘，`scada.replay.path` 指向数据盘。

五是**状态机的 ERROR 态要有人工介入出口**。当前实现 ERROR 设备永远返回 null，需要管理员手动改 `status` 才能恢复。商用版应加"ERROR 超过 N 分钟自动降级到 RECONNECTING 重试一次"的逻辑，避免设备永远卡死。

## 九、商用化检查清单

- 调度线程是 daemon 吗？应用关停时能不能优雅退出？`@PreDestroy` 里 `scheduler.shutdown()` + `awaitTermination` 验证过吗？
- in-flight 防重有没有内存泄漏？任务异常没走到 finally 会让 runningTaskIds 永不清理——确保 finally 一定执行。
- 断线重连日志够不够安静？同一设备 1 秒内只打一次重连失败日志，否则日志会刷屏。
- ReplayBuffer 容量告警有没有？快满时要告警，否则数据悄悄被淘汰。
- TDengine 恢复后回放速度有没有限速？一次性 drain 10w 条冲击 TDengine 写入，应该分批每秒回放 1w 条。
- 线程池参数能不能动态调？生产环境 PLC 数量变了要调 core/max，最好接 yudao 的配置中心热更新。
- 设备状态变更有没有事件通知？设备从 CONNECTED 掉到 RECONNECTING 应该推 SSE 给前端，运维要第一时间看到。

到这里，采集调度的"什么时候读"、断线重连的"掉了怎么回来"、补采的"数据往哪放"都讲完了。scada-collect 的核心运行时也就闭环了——从 1Hz 扫表触发，到 Driver 读、过滤坏值、写 TDengine、推 SSE、进告警引擎，再到断线指数退避重连、TDengine 挂了 RocksDB 补采，整条数据链路都有兜底。

这个连载到此告一段落。后续章节会展开告警引擎（ISA-18.2 状态机 + on/off-delay 抖动抑制）、SSE 推送聚合、TDengine 超表设计与历史曲线查询，那些是 SCADA 的"上层应用"，建立在前面四章打的这个底座之上。
