# 06 - 告警引擎 ISA-18.2 与抖动抑制

## 一、痛点引入

上一章我把 TDengine 时序库接通了，写入顺滑。但工业现场有个潜规则：**数据存进库不算完成，告警触发才是 SCADA 真正的输出**。运维人员盯着大屏上的实时曲线是一回事，半夜告警把他叫起来又是另一回事。

我最早实现的告警逻辑是裸 if：

```java
if (value > rule.getHighLimit()) {
    smsService.send(onCallPhone, "告警：" + rule.getName());
}
```

上线第一天就被骂死。设备刚开机 PLC 寄存器读到 0，下一秒跳到正常值，阈值规则触发；Modbus 通讯抖动一次读到 -1，又触发；电网一次毛刺让温度瞬间过阈值然后立刻回来，触发 → 自动复归 → 再触发，10 分钟刷了 80 条短信。运维把电话打过来："你能不能别给我发短信了？"

更糟糕的是状态没记录。一条告警短信发出去后，运维不点确认的话系统不会知道他看过没看过；过 5 分钟值正常了系统也不复归；多人同时值班时谁都以为对方处理了。这就是工业控制里典型的"告警洪流"和"无人值守"问题。

工业界针对这个问题有现成标准——ANSI/ISA-18.2《Alarm Management》。这一章就讲我怎么把这个标准简化后落地到 Yudao 框架里。

## 二、行业对比：ISA-18.2 vs OPC UA A&C vs 裸阈值比较

| 维度 | ISA-18.2 | OPC UA A&C | 裸阈值比较 |
|---|---|---|---|
| 标准化 | ANSI 国际标准 | OPC UA 规范 Part 10 | 无 |
| 状态机 | 4-7 态生命周期 | 类似 4 态 | 无状态 |
| 抖动抑制 | on/off-delay、deadband | on-delay | 无 |
| 优先级 | 4 级严重度 | 严重度 + 分组 | 无 |
| 实施成本 | 中（DB+逻辑） | 高（OPC UA Server） | 极低 |
| 适用场景 | 工业告警全生命周期 | 设备级告警集成 | 简单监控 |

OPC UA A&C（Alarms & Conditions）规范几乎覆盖 ISA-18.2 全部概念，但实施它需要起一个 OPC UA Server，要管 UA 二进制协议栈、订阅模型、节点命名空间。Yudao 是 Web 后端框架，没必要为了告警单独引整套 OPC UA 栈。我用 ISA-18.2 概念 + 自己实现的状态机，性能更好，跟 Spring Bean 体系融合也更顺。

裸阈值比较方案根本不用考虑——状态、抖动、优先级、通知路由一个都没有，工业现场不可用。

## 三、选型与设计取舍

**为什么只保留 5 态，不是 ISA-18.2 全部 7 态？** ISA-18.2 完整版有 Normal、Unack、Acked、RTN-Unack、RTN-Acked、Shelved、Suppressed By Design 共 7 态。我做了三处简化：

- `RTN-Acked` 合并到 `Normal`：已确认且复归的事件在业务上已经闭环，归档即可，不再让它占状态枚举；
- `Suppressed By Design` 用 `rule.enabled=false` 表达，不进状态机；
- `Shelved` 状态值上保留（9），但实际生效路径是 `enabled=false`，状态机只过 4 条主线转移。

最终状态枚举是 5 个：`NORMAL / UNACK / ACKED / RTN_UNACK / SHELVED`。状态转移是 5 条：`NORMAL→UNACK→ACKED→NORMAL` 主线 + `UNACK→RTN_UNACK→NORMAL` 复归支线。覆盖 95% 工业告警场景，状态机简单不会写错。

**为什么 AlarmStateMachine 是纯函数而不是 @Component？** 状态机本身不带状态，状态都存在 `scada_alarm_event.state` 字段里，状态机只做"from→to 是否合法"的判断。纯函数工具类没状态好测好并发，没有任何注入字段。它被 `AlarmEngine` 调用、被 `AlarmEventService` 调用，两边各取所需。

**on-delay 抖动抑制**。继电器延时线圈那套机制。条件满足不立刻触发，要持续 N 毫秒才正式产生告警事件。场景有三：

- 瞬时尖峰：电网毛刺让温度瞬间过阈值 200ms，不该告警；
- PLC 重启值跳变：PLC 上电瞬间寄存器读 0 或 -1，几秒后才稳定；
- 阈值边界抖动：值在阈值附近上下漂动，不该反复触发-复归。

**off-delay 默认 5s 比 on-delay 2s 长**。复归延迟要长得多的核心原因是：工业告警宁可多触发不可多复归。复归过快导致运维误以为问题已解决，结果值又上来了，告警洪流。复归 5s 是从工况角度反推的：温度从 80° 降到 75° 一般要几秒甚至几十秒，5s 复归能过滤掉所有非真实复归。

**规则全量入内存不查 DB**。告警引擎每秒被采集任务调用一次（1Hz），每次 onValues 可能评估几百条点位值。如果每次都 `ruleMapper.selectByPointId(pointId)` 走 MySQL 查规则，主库连接池瞬间被打爆。所以 `@PostConstruct` 启动时一次性 `selectAllEnabled` 全量加载到 `Map<pointId, List<rule>>` 内存，规则变更时通过 `alarmEngine.reloadRules()` 显式刷新。这是工业 SCADA 标准做法，Wonderware / iFix 都这么干。

**peakValue 怎么追踪**。一次告警事件从触发到复归期间可能持续数小时，期间值上下波动。`peakValue` 记录触发期间的极值，事后复盘能知道"这次过载到底严重到什么程度"。实现上每次值进来都跟当前 peakValue 比，超过就更新——简化版直接 `updateById`，商用版应批量合并避免高频写库。

### 4.1 状态枚举与状态机

`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/enums/ScadaAlarmState.java`：

```java

    NORMAL(0, "正常"),
    UNACK(1, "未确认"),
    ACKED(2, "已确认"),
    RTN_UNACK(3, "复归未确认"),
    SHELVED(9, "已屏蔽");
}
```

`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/framework/scada/alarm/AlarmStateMachine.java`：

```java
public final class AlarmStateMachine {

    private AlarmStateMachine() {}

    public static boolean canTransit(Integer from, Integer to) {
        if (from == null) return to.equals(ScadaAlarmState.UNACK.getState());
        int f = from;
        int t = to;
        if (f == t) return false;
        return (f == ScadaAlarmState.NORMAL.getState() && t == ScadaAlarmState.UNACK.getState())
                || (f == ScadaAlarmState.UNACK.getState() && t == ScadaAlarmState.ACKED.getState())
                || (f == ScadaAlarmState.UNACK.getState() && t == ScadaAlarmState.RTN_UNACK.getState())
                || (f == ScadaAlarmState.ACKED.getState() && t == ScadaAlarmState.NORMAL.getState())
                || (f == ScadaAlarmState.RTN_UNACK.getState() && t == ScadaAlarmState.NORMAL.getState());
    }

    public static Integer ackTarget(Integer from) {
        if (from == null) return null;
        if (from.equals(ScadaAlarmState.UNACK.getState())) return ScadaAlarmState.ACKED.getState();
        if (from.equals(ScadaAlarmState.RTN_UNACK.getState())) return ScadaAlarmState.NORMAL.getState();
        return null;
    }

    public static Integer clearTarget(Integer from) {
        if (from == null) return null;
        if (from.equals(ScadaAlarmState.UNACK.getState())) return ScadaAlarmState.RTN_UNACK.getState();
        if (from.equals(ScadaAlarmState.ACKED.getState())) return ScadaAlarmState.NORMAL.getState();
        return null;
    }
}
```

注意两点：

- 类是 `final` + 私有构造，纯函数工具；
- `ackTarget` 和 `clearTarget` 返回目标态或 null——null 表示"当前态不允许这个操作"，业务层据此报错或忽略。

### 4.2 AlarmEngine 主流程

`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/service/alarm/AlarmEngine.java`。先看启动加载和路由：

```java
@PostConstruct
public void loadRules() {
    reloadRules();
}

public void reloadRules() {
    List<ScadaAlarmRuleDO> all = ruleMapper.selectAllEnabled();
    Map<Long, List<ScadaAlarmRuleDO>> grouped = new HashMap<>();
    for (ScadaAlarmRuleDO r : all) {
        grouped.computeIfAbsent(r.getPointId(), k -> new ArrayList<>()).add(r);
    }
    rulesByPoint.clear();
    rulesByPoint.putAll(grouped);
    log.info("AlarmEngine 加载 {} 条规则覆盖 {} 个点位", all.size(), grouped.size());
}

public void onValues(List<PointValue> values) {
    for (PointValue v : values) {
        if (!v.isGood()) continue;
        if (v.valueNum() == null) continue;
        List<ScadaAlarmRuleDO> rules = rulesByPoint.get(v.pointId());
        if (rules == null || rules.isEmpty()) continue;
        for (ScadaAlarmRuleDO rule : rules) {
            try {
                evaluateRule(rule, v);
            } catch (Exception e) {
                log.warn("规则 {} 判定失败: {}", rule.getCode(), e.getMessage());
            }
        }
    }
}
```

`reloadRules` 是全量替换——先 `clear()` 再 `putAll`，配合 `ConcurrentHashMap` 实现并发安全。规则变更期间的"读到旧规则"和"读到新规则"混杂很正常，不影响告警正确性，下一秒就一致了。

`onValues` 按 `pointId` 路由到该点位挂的规则集合，单条规则失败不影响其他规则评估（catch 包裹）。

### 4.3 抖动抑制核心

```java
private void evaluateRule(ScadaAlarmRuleDO rule, PointValue value) {
    boolean triggered = isTriggered(rule, value.valueNum());
    String key = rule.getId() + ":" + value.pointId();
    PendingState pending = pendingStates.computeIfAbsent(key, k -> new PendingState());
    long now = System.currentTimeMillis();

    ScadaAlarmEventDO activeEvent = eventMapper.selectActiveByRule(rule.getId());

    if (triggered) {
        if (activeEvent == null) {
            if (pending.triggerStartMs == 0) {
                pending.triggerStartMs = now;
            }
            if (now - pending.triggerStartMs >= rule.getOnDelayMs()) {
                createEvent(rule, value, activeEvent);
                pending.triggerStartMs = 0;
                pending.clearStartMs = 0;
            }
        } else {
            pending.clearStartMs = 0;
            tryUpdatePeak(activeEvent, value.valueNum());
        }
    } else {
        if (activeEvent != null) {
            if (pending.clearStartMs == 0) {
                pending.clearStartMs = now;
            }
            if (now - pending.clearStartMs >= rule.getOffDelayMs()) {
                clearEvent(activeEvent);
                pending.clearStartMs = 0;
                pending.triggerStartMs = 0;
            }
        } else {
            pending.triggerStartMs = 0;
        }
    }
}
```

逻辑分四个分支，我用大白话解释：

1. **触发条件满足 + 还没有 active 事件**：开始记时，连续超过 `onDelayMs` 没断过 → 真告警，插入事件。期间若任何一次值不满足触发条件，下一次 evaluateRule 会落到分支 4，把 `triggerStartMs` 清零，倒计时重来。这就是抖动抑制的本质——条件要"持续"满足，不能瞬时尖峰带过。

2. **触发条件满足 + 已有 active 事件**：清掉复归倒计时（因为又满足了），同时更新峰值。这一步防止"抖一下不满足→抖一下满足"导致复归计时器被反复清零但又不复归，确保只有连续不满足才复归。

3. **触发条件不满足 + 有 active 事件**：开始记复归倒计时，连续超过 `offDelayMs` 才复归。中间任何一次满足触发条件，下一次评估回到分支 2 把 `clearStartMs` 清零。

4. **触发条件不满足 + 无事件**：清掉触发倒计时。这是抖动抑制的关键防御——一次瞬时尖峰触发了 `triggerStartMs`，但下一次又不满足了，立刻清零，下轮从 0 开始。

`PendingState` 是一个内部静态类，只有 `triggerStartMs` 和 `clearStartMs` 两个 long 字段。每个 (ruleId, pointId) 一份，存在 `ConcurrentHashMap<String, PendingState>`。

### 4.4 三种规则判定

```java
private boolean isTriggered(ScadaAlarmRuleDO rule, BigDecimal value) {
    double v = value.doubleValue();
    Integer type = rule.getRuleType();
    if (type.equals(ScadaAlarmRuleType.THRESHOLD.getType())) {
        boolean highHit = rule.getHighLimit() != null && v > rule.getHighLimit().doubleValue();
        boolean lowHit = rule.getLowLimit() != null && v < rule.getLowLimit().doubleValue();
        return highHit || lowHit;
    }
    if (type.equals(ScadaAlarmRuleType.BAND.getType())) {
        boolean outHigh = rule.getHighLimit() != null && v > rule.getHighLimit().doubleValue();
        boolean outLow = rule.getLowLimit() != null && v < rule.getLowLimit().doubleValue();
        return outHigh || outLow;
    }
    if (type.equals(ScadaAlarmRuleType.RATE.getType())) {
        return rule.getRateLimit() != null && Math.abs(v) > rule.getRateLimit().doubleValue();
    }
    return false;
}
```

`THRESHOLD` 和 `BAND` 在当前实现里逻辑相近（都是上下限超限触发），区别在语义：`THRESHOLD` 表达"超限即异常"，`BAND` 表达"出区间即异常"，未来给 `BAND` 加 deadband 时差别就出来了——`BAND` 死区是双向的，`THRESHOLD` 是单向的。

`RATE` 实现是简化版，没有真正算 `Δv/Δt`，因为需要维护前一次值。完整版应在 `PendingState` 里加 `prevValue` 和 `prevTs`，当前实现只在注释里标了"参见 v2"。这是商用版的 TODO 之一。

### 4.5 事件创建与峰值追踪

```java
private void createEvent(ScadaAlarmRuleDO rule, PointValue value, ScadaAlarmEventDO oldEvent) {
    ScadaAlarmEventDO event = ScadaAlarmEventDO.builder()
            .ruleId(rule.getId())
            .pointId(value.pointId())
            .deviceId(null)
            .triggeredAt(LocalDateTime.now())
            .triggerValue(value.valueNum())
            .peakValue(value.valueNum())
            .state(ScadaAlarmState.UNACK.getState())
            .severity(rule.getSeverity())
            .message(buildMessage(rule, value))
            .notified(false)
            .build();
    eventMapper.insert(event);
    log.info("告警触发 rule={} value={} event={}", rule.getCode(), value.valueNum(), event.getId());
    try {
        notifyRouter.notify(event, rule);
        event.setNotified(true);
        eventMapper.updateById(event);
    } catch (Exception e) {
        log.warn("告警通知失败 event={}: {}", event.getId(), e.getMessage());
    }
}

private void tryUpdatePeak(ScadaAlarmEventDO event, BigDecimal value) {
    if (event.getPeakValue() == null || value.compareTo(event.getPeakValue()) > 0) {
        event.setPeakValue(value);
        eventMapper.updateById(event);
    }
}
```

`peakValue` 一开始等于 `triggerValue`，每次有新值进来跟当前 peak 比较，比它大就更新。复归时 `clearEvent` 会把 `peakValue` 写回：

```java
private void clearEvent(ScadaAlarmEventDO event) {
    Integer toState = AlarmStateMachine.clearTarget(event.getState());
    if (toState == null) return;
    eventMapper.updateCleared(event.getId(), toState, LocalDateTime.now(), event.getPeakValue());
    log.info("告警复归 event={} state {}->{}", event.getId(), event.getState(), toState);
}
```

`updateCleared` 是 MyBatis-Plus 的条件 update，必须带 `WHERE id=? AND state=?` 才能成功，否则返回 0 表示状态已被其他线程改了——这就是状态机的并发安全防线。

### 4.6 通知路由按严重度分发

`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/service/alarm/AlarmNotifyRouter.java`：

```java
public void notify(ScadaAlarmEventDO event, ScadaAlarmRuleDO rule) {
    Integer severity = event.getSeverity() == null ? rule.getSeverity() : event.getSeverity();
    if (severity == null) severity = ScadaAlarmSeverity.MEDIUM.getSeverity();

    if (severity.equals(ScadaAlarmSeverity.LOW.getSeverity())) {
        log.info("告警通知[LOW] event={} rule={}: 仅记日志", event.getId(), rule.getCode());
        return;
    }
    if (severity.equals(ScadaAlarmSeverity.MEDIUM.getSeverity())) {
        log.info("告警通知[MEDIUM] event={} rule={}: 写入通知表", event.getId(), rule.getCode());
        return;
    }
    if (severity.equals(ScadaAlarmSeverity.HIGH.getSeverity())) {
        log.warn("告警通知[HIGH] event={} rule={} msg={}: 站内+短信",
                event.getId(), rule.getCode(), event.getMessage());
        return;
    }
    if (severity.equals(ScadaAlarmSeverity.CRITICAL.getSeverity())) {
        log.error("告警通知[CRITICAL] event={} rule={} msg={}: 站内+短信+电话+微信",
                event.getId(), rule.getCode(), event.getMessage());
        return;
    }
}
```

四级路由：LOW=仅日志、MEDIUM=通知表、HIGH=站内+短信、CRITICAL=全渠道（含电话语音）。电话语音是关键场景——核反应堆/电力调度凌晨告警必须电话叫人，APP 推送指望不上，用户夜间不开手机。我留了注释指向阿里云语音/容联云通讯，商用版在这里真正接通。

## 五、调优与踩坑

**坑一：`selectActiveByRule` 每次 evaluateRule 都查库**。当前实现里每次评估都 `eventMapper.selectActiveByRule(rule.getId())` 查一次 active 事件，1Hz × 1000 规则就是 1000 次/秒查库。商用版应缓存"当前每个 rule 的 active event id"，事件创建/复归时同步更新缓存，把这条查询打掉 99%。

**坑二：peakValue 高频更新**。`tryUpdatePeak` 里每次超过峰值就 `updateById`，一次告警持续一小时可能产生上百条 update。应改成"内存里追踪 peak，复归时一次性写回"。当前实现是简化版，商用版必须改。

**坑三：on-delay 默认 2s 对慢变量太短**。温度、压力这类慢变量从异常工况发展到危险要几十秒，2s on-delay 反而把瞬时干扰放过去。慢变量规则应配 on-delay 5-10s，快变量（电流、电压）才用 2s。规则编辑界面要让用户选预设模板。

**坑四：rate 规则没维护 prevValue**。当前 RATE 实现只是判断 `|v| > rateLimit`，不是真正的变化率。我承认这是个 TODO——简化版先跑通，商用版必须在 PendingState 加 `prevValue` 和 `prevTs`，`(v - prevValue) / (ts - prevTs) * 1000` 才是真正的 rate。

**坑五：规则变更期间内存 Map clear+putAll 不是原子的**。极端情况下 `clear()` 后另一个线程读 `rulesByPoint.get(pid)` 拿到 null 跳过本批告警，下一秒就恢复。丢一拍告警可接受，但如果业务要严格不丢，应用 `ConcurrentHashMap.replace` 原子替换引用。

## 六、商用化检查清单

- [ ] on-delay/off-delay 按变量动态属性预设（慢变量长 / 快变量短）
- [ ] 死区 deadband 实现（避免阈值附近抖动，目前字段留着未用）
- [ ] RATE 规则补完 prevValue/prevTs 真变化率
- [ ] active event 缓存减少 DB 查询
- [ ] peakValue 内存追踪 + 复归时一次性写回
- [ ] 通知防抖：同一 rule 同一 severity 短时间内重复事件合并
- [ ] ack 操作加权限校验（只有值班人能 ack）
- [ ] CRITICAL 渠道真接通电话语音
- [ ] 告警事件归档策略（90 天后冷归档，对应 `scada.alarm.retain-days: 90`）
- [ ] 监控指标：未确认事件数、平均 ack 时延、告警频次 topN
- [ ] 告警抑制规则：相关告警同时触发时只通知根因
- [ ] Shelved 状态机内联化，而不是仅靠 enabled=false
