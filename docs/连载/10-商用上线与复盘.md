# 10-商用上线与复盘

## 一、痛点引入

最后一章了，得说点不好听的真话。

第一周上线，客户工厂 30 台 PLC、每台平均 50 个点位、合计 1500 个点位 1Hz 采集。理论吞吐 1500 points/s，按 README 写的"TDengine 写入上限 100w points/s"，看起来距离天花板还有三个数量级，应该很稳。

实际跑三天，第四天早上客户来电话：早 8 点交接班看板打不开，转圈。我远程上去一看，OOM Killer 把 yudao 进程杀了。原因不在 TDengine，在 RocksDB——ReplayBuffer 在某次断网期写满 100w 条（配置上限）后，磁盘写了 4GB，JVM heap 占用飙到 3GB，原因不是 RocksDB 本身的内存，而是 `ReplayBuffer` 在做 LRU 淘汰时整批把 RocksDB 的 iterator 加载到 heap 里。

这是单实例方案最真实的代价。这一章就把"商用上线"这件事彻底扒开——边界在哪里、瓶颈在哪里、ISA-18.2 简化版漏了什么、上线前 5 项必做检查。

## 二、行业对比

工业 SCADA 的部署架构大概三类：

- **单实例 + 本地存储**：传统 WinCC/iFIX，一台工控机扛一个车间，备份靠人手动。
- **双机热备 + 共享存储**：Wonderware/Honeywell 这种商用大件，主备切换走 keepalive 或仲裁。
- **分布式 + 时序库 + 消息队列**：开源 IoT 平台（ThingsBoard、IoTDB）走的就是这套。

我这套 `scada-collect` 走的是第一类：单实例 + RocksDB 本地补采 + TDengine 集中存储。理由很务实——中小制造工厂 95% 用不到多活，多活需要分布式锁、需要跨节点状态同步、需要 Redis，工业现场没这条件也没这预算。这套设计在 95% 的中小制造场景里是甜点，剩下 5% 必须升级多活时再说。

ISA-18.2 标准告警生命周期，简化版我做了三处裁剪，下面踩坑段会讲。

## 三、选型与设计取舍

### 1. 单实例部署的边界在哪里

单实例的硬边界有四个：

- **设备数 > 200 台**：`scadaCollectExecutor` 默认 max=32，按每台 2 个并行任务算 200 台勉强能撑；超过 200 台建议拆分实例。
- **点位数 > 5w**：TDengine 单节点写入上限 ~100w points/s，但单节点查询会拖，看板响应变慢。
- **客户端 SSE 连接数 > 500**：`SsePushServer` 的 `pendingValues` 是全客户端共享 Map，500 客户端 × 500 点位 = 25w 并发推送，单线程聚合会成瓶颈。
- **要求 RPO < 0（不允许丢任何数据）**：单实例宕机瞬间的 buffer 数据会丢，RocksDB 也不能保证不丢。

### 2. 什么场景必须升级多活

四个边界任一被打破就要升级多活。多活的技术代价是：

- 设备 → 实例的分配要走一致性哈希 + 分布式锁（Redis 或 etcd）
- AlarmEngine 的 `pendingStates` Map 必须改成 Redis 共享，否则抖动抑制计数会丢
- ReplayBuffer 必须改成 Kafka 之类的分布式队列
- SSE 推送必须走网关层做粘性会话

简单算一笔账：多活方案至少加 Redis 1 台、Kafka 3 台、网关 1 台——硬件成本翻三倍，运维成本翻五倍。中小制造工厂不值的，所以这套方案就是为单实例优化的。

### 3. ReplayBuffer 单机 RocksDB 的运维风险

风险分三个：

- **磁盘写放大**：RocksDB LSM tree 的 compaction 会产生 5-10 倍写放大，预估 200MB 实际占盘可能到 2GB。
- **运维不可视**： RocksDB 的 sst 文件二进制不可读，出问题只能靠 `RocksDB` 自带 stats，运维同学上手成本高。
- **跨节点不共享**：一旦做主备切换，备机没有 buffer 数据，断网期数据丢。

我做这套方案时已经知道这三个风险，权衡的是"工业现场 95% 不需要多活"。下次大版本会提供 Kafka 后端作为可选实现。

### 4. TDengine 100w points/s 上限怎么测出来的

不是纸上谈兵。我在测试机（i7-12700 / 32GB / NVMe SSD）跑了 `PointValueServiceImpl.batchInsert` 的压测脚本，单节点 100w points/s 写入 30 分钟，CPU 80%、磁盘 IO 60%、TDengine 进程稳定。100w 是当时实测的稳定吞吐，再往上 IO 就是瓶颈。

但是——这是测试机的数字。生产环境如果是 4 核 8G 的虚拟机，实测可能掉到 30w。所以 README 写"100w points/s（单节点）"是上限不是常态，客户现场要按 1/3 估算。

### 5. SSE 500 点位/客户端上限的真实瓶颈在哪

瓶颈不在 TDengine、不在网络，在 `SsePushServer.flushAll`：

```java
private void flushAll() {
    if (pendingValues.isEmpty() || emitters.isEmpty()) return;
    Map<Long, PointValue> snapshot = new HashMap<>(pendingValues);
    pendingValues.clear();
    for (Map.Entry<String, Set<Long>> e : connSubscriptions.entrySet()) {
        // ... 拼帧、emitter.send ...
    }
}
```

`flushAll` 是**单线程**调度，1Hz 一次。假设 100 个客户端每个订阅 500 个点位，单帧拼装要遍历 5w 个 `(clientId, pointId)` 对，加上 JSON 序列化，单次 flush 可能要 200ms。如果客户端再多一点，单次 flush 就超过 1s，聚合周期被打散，前端实际看到的是 2Hz 推送而非 1Hz。

500 上限是我实测下"100 客户端 × 500 点位仍能稳定 1Hz"的边界。要破这个上限，得把 `flushAll` 改成多线程分片——商用 v2 在做的事。

### 6. ISA-18.2 简化版漏掉了什么

完整的 ISA-18.2 告警生命周期有十几个状态，我简化成了五个（NORMAL/UNACK/ACKED/RTN_UNACK/SHELVED）。漏掉的真实工业现场需要的特性：

- **Suppressed By 原因**：运维手动屏蔽告警时要记录原因（"维护中"、"传感器故障"），我只走 `rule.enabled=false`，没记原因。
- **Chattering/Re-alarm 节流**：同一个告警短时间内反复触发-复归要自动抑制一段时间，我没实现，靠 on/off-delay 间接缓解。
- **跨点关联告警**：两个点位同时超限才算告警（如"温度高且压力高"），我只做单点告警，多点位关联要靠 AlarmEngine 自己手写复合条件。
- **Ack 委派**：操作员把告警转给另一人确认，我没实现 Ack 转移。
- **告警优先级动态调整**：高峰期自动降低低级告警优先级，我没做。

这五条是商用工业 SCADA 现场真正需要的，我承认这套简化版只覆盖了 80% 场景。剩下 20% 要在 v2 补。

## 四、关键代码精讲

### 4.1 DeviceConnectionManager 双守护线程

文件：`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/service/collect/DeviceConnectionManager.java`

两个守护线程：重连守护（500ms 扫一次）+ 心跳守护（60s 扫一次）。

```java
private void startReconnectDaemon() {
    Thread t = new Thread(() -> {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                long now = System.currentTimeMillis();
                for (Map.Entry<Long, ReconnectState> e : reconnectStates.entrySet()) {
                    ReconnectState s = e.getValue();
                    if (now < s.nextAttemptAt) continue;
                    ScadaDeviceDO device = deviceCache.get(e.getKey());
                    if (device == null) {
                        reconnectStates.remove(e.getKey());
                        continue;
                    }
                    tryReconnect(device);
                }
                Thread.sleep(500);
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }, "scada-reconnect");
    t.setDaemon(true);
    t.start();
}
```

心跳守护判定超时：

```java
private void startHeartbeatWatchdog() {
    Thread t = new Thread(() -> {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                Thread.sleep(60_000);
                LocalDateTime cutoff = LocalDateTime.now().minusSeconds(30);
                for (Map.Entry<Long, ScadaDeviceDO> e : deviceCache.entrySet()) {
                    ScadaDeviceDO d = e.getValue();
                    if (Boolean.FALSE.equals(d.getEnabled())) continue;
                    if (!ScadaDeviceStatus.CONNECTED.getState().equals(d.getStatus())) continue;
                    if (d.getLastHeartbeatAt() == null || d.getLastHeartbeatAt().isBefore(cutoff)) {
                        onConnectionError(d.getId(), "心跳超时 30s");
                    }
                }
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }, "scada-heartbeat");
    t.setDaemon(true);
    t.start();
}
```

指数退避计算：

```java
private long computeBackoffMs(int attempt) {
    long base = 1000L * (1L << Math.min(attempt, 5));
    return Math.min(base, 30_000);
}
```

`Math.min(attempt, 5)` 把位移封顶在 5，对应 1/2/4/8/16/30s 序列；`Math.min(base, 30_000)` 二次封顶 30s。这两个封顶是工业现场的血泪——早期版本没封顶，一台长期断线的设备每次重连都指数往上爬，跑了几小时后台睡了几个月才唤醒。

### 4.2 AlarmEngine 规则全量入内存

文件：`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/service/alarm/AlarmEngine.java`

```java
@PostConstruct
public void loadRules() {
    reloadRules();
}

public void reloadRules() {
    List<ScadaAlarmRuleDO> all = ruleMapper.selectAllEnabled();
    Map<Long, List<ScadaAlarmRuleDO>> grouped = new HashMap<>();
    for (ScadaAlarmRuleDO r : all) {
        grouped.computeIfAbsent(r.getPointId(), k -> new ArrayList<>()).add(r);
    }
    rulesByPoint.clear();
    rulesByPoint.putAll(grouped);
    log.info("AlarmEngine 加载 {} 条规则覆盖 {} 个点位", all.size(), grouped.size());
}
```

策略是**启动时全量加载 + 规则变更时全量重载**。`onValues` 收到一批值时按 pointId 路由到规则列表：

```java
public void onValues(List<PointValue> values) {
    for (PointValue v : values) {
        if (!v.isGood()) continue;
        if (v.valueNum() == null) continue;
        List<ScadaAlarmRuleDO> rules = rulesByPoint.get(v.pointId());
        if (rules == null || rules.isEmpty()) continue;
        for (ScadaAlarmRuleDO rule : rules) {
            try {
                evaluateRule(rule, v);
            } catch (Exception e) {
                log.warn("规则 {} 判定失败: {}", rule.getCode(), e.getMessage());
            }
        }
    }
}
```

为什么全量入内存而不是按需查 DB？因为告警判定是高频热路径，每次都查 DB 必死。全量入内存的代价是规则变更时需要 reload，但规则变更频率低（一周一次），跟 1Hz 判定比完全可接受。

抖动抑制的核心逻辑：

```java
if (triggered) {
    if (activeEvent == null) {
        if (pending.triggerStartMs == 0) {
            pending.triggerStartMs = now;
        }
        if (now - pending.triggerStartMs >= rule.getOnDelayMs()) {
            createEvent(rule, value, activeEvent);
            pending.triggerStartMs = 0;
            pending.clearStartMs = 0;
        }
    } else {
        pending.clearStartMs = 0;
        tryUpdatePeak(activeEvent, value.valueNum());
    }
}
```

`pending.triggerStartMs` 记的是"条件开始满足的时间戳"，超过 `onDelayMs` 才真正产生事件。这是工业 SCADA 标准做法，simscape/wonderware 都这么干。

### 4.3 SsePushServer 30min timeout + 1Hz flush

文件：`yudao-module-scada/src/main/java/cn/iocoder/yudao/module/scada/framework/scada/sse/SsePushServer.java`

```java
public class SsePushServer {
    private static final long TIMEOUT_MS = 30 * 60 * 1000L;

    private final Map<String, SseEmitter> emitters = new ConcurrentHashMap<>();
    private final Map<String, Set<Long>> connSubscriptions = new ConcurrentHashMap<>();
    private final Map<Long, PointValue> pendingValues = new ConcurrentHashMap<>();

    private final ScheduledExecutorService aggregator = Executors.newSingleThreadScheduledExecutor(
            r -> { Thread t = new Thread(r, "scada-sse-agg"); t.setDaemon(true); return t; });

    public SsePushServer() {
        aggregator.scheduleAtFixedRate(this::flushAll, 1, 1, TimeUnit.SECONDS);
    }
}
```

30min timeout 是关键。SSE 长连接超过这个时间会主动断开，前端 `EventSource` 会自动重连。这个值不是随便定的——浏览器默认 EventSource 重连间隔 3s，30min 一次断开重连的代价可接受；如果设成 60min，某些反向代理（nginx 默认 60s 读超时）会先于应用断开。

1Hz flush 是聚合的关键。看 `flushAll`：

```java
private void flushAll() {
    if (pendingValues.isEmpty() || emitters.isEmpty()) return;
    Map<Long, PointValue> snapshot = new HashMap<>(pendingValues);
    pendingValues.clear();
    for (Map.Entry<String, Set<Long>> e : connSubscriptions.entrySet()) {
        // 拼帧、emitter.send
    }
}
```

`pendingValues` 是全局共享的——多个 Driver 写入、单个聚合线程消费，快照后清空。1Hz 是"工业监控节奏"——人眼观察设备状态 1 秒一帧足够，再快人也看不过来。

### 4.4 6 个枚举语义复盘

最后一次把 6 个枚举的语义总览：

- `ScadaProtocolType`：6 个值（10=ModbusTCP/11=ModbusRTU/20=OPCUA/30=S7-1200/31=S7-1500/40=MQTTSparkplugB）。决定 Driver 选择。
- `ScadaPointType`：4 个值（BOOL/INT/FLOAT/STR）。决定 TDengine 子表列类型推导（BOOL→BOOL, INT→BIGINT, FLOAT→DOUBLE, STR→NCHAR(64)）。
- `ScadaDeviceStatus`：6 个值（DISABLED/UNKNOWN/CONNECTING/CONNECTED/RECONNECTING/ERROR）。`DeviceConnectionManager` 状态机。
- `ScadaAlarmState`：5 个值（NORMAL/UNACK/ACKED/RTN_UNACK/SHELVED）。ISA-18.2 简化版。
- `ScadaAlarmRuleType`：3 个值（THRESHOLD/BAND/RATE）。三种最基础告警规则。
- `ScadaAlarmSeverity`：4 个值（LOW/MEDIUM/HIGH/CRITICAL）。决定通知路由。

6 个枚举加起来 28 个值，覆盖整个系统的状态空间。这套枚举的设计原则是"宁少勿多"——不为了"看起来完备"塞 ISA-18.2 完整版的十几个状态，工业现场不需要的状态就是负担。

## 五、调优与踩坑

**踩坑 1：ReplayBuffer LRU 淘汰吃 heap。** 这个痛点引入讲过。修复方案是改用 RocksDB 的 `RocksIterator` 流式扫描，不一次性加载到 heap。生产已上线，但 v1 代码里这版还没合入。

**踩坑 2：AlarmEngine 高频 update 写穿 TDengine。** `tryUpdatePeak` 每次都 `eventMapper.updateById`，一次告警事件持续期间，如果点值每秒变化 1Hz，事件被 update 1 次/秒。10 万条 active 事件时 MySQL 写入压力极大。商用版应该批量合并，比如每 5s 聚合一次 peak 更新。

**踩坑 3：SSE 1Hz flush 超时。** 客户端超过 100 个时单次 flush 超过 1s，聚合周期被打散。临时方案是把 `flushIntervalMs` 改成 2000ms（0.5Hz），治标；根治是改成多线程分片 flush。

**调优：心跳 cutoff 调到 60s。** 默认 30s，工业现场偶发网络抖动会被误判断线，触发重连风暴。建议改成 60s，给网络抖动一些容错。

**调优：onDelayMs 默认 2s，offDelayMs 默认 5s。** 这套默认值是工业现场经验值——onDelay 短了误报多、长了关键告警延迟；offDelay 长了状态切换慢、短了抖动多。客户具体场景按这俩默认值 ±50% 调。

**踩坑 4：TDengine 子表过多。** 万级点位 = 万级子表，TDengine 默认 `vgroup` 数有限，子表数过多会触发 schema 检查慢。生产建议把 `tdengine` 的 `maxVgroupsPerVnode` 调到 1000 以上。

## 六、商用上线 5 项必做检查

最后一节，给一套上线前的硬性 checklist：

### 1. 监控

- [ ] JVM heap + GC 曲线接入 Prometheus，alert 阈值 heap>80% 持续 5min
- [ ] `scadaCollectExecutor` 池活跃线程数、队列堆积数接入监控
- [ ] `DeviceConnectionManager` 的 RECONNECTING 设备数接入监控，超 5 台立刻告警
- [ ] TDengine 写入 QPS、查询延迟接入监控
- [ ] RocksDB 磁盘占用接入监控，超 4GB 告警

### 2. 备份

- [ ] MySQL 5 张业务表每天 mysqldump 一次，保留 30 天
- [ ] TDengine 每周 taosdump 一次，保留 4 周
- [ ] RocksDB 路径每日增量备份到独立磁盘
- [ ] 备份恢复演练至少做一次，确认能起来

### 3. 降级

- [ ] `scada.collect-enabled=false` 灰度开关演练过一次
- [ ] SSE 流量超阈值时降级策略（关停部分客户端）演练过
- [ ] TDengine 不可用时 ReplayBuffer 兜底策略验证过
- [ ] 单台 Driver 故障不影响其他设备的隔离性验证过

### 4. 压测

- [ ] 真实设备数 × 1.5 倍点位数 1Hz 持续 30 分钟压测
- [ ] 模拟 100 个 SSE 客户端同时订阅 500 点位压测
- [ ] 模拟 10 台设备同时断线触发重连风暴压测
- [ ] ReplayBuffer 写满 100w 条的内存峰值压测

### 5. 安全

- [ ] TDengine 密码不在 git、不在镜像 layer、不在配置中心
- [ ] 6 个 Controller 都过了 yudao RBAC 权限校验
- [ ] `X-Operator` 网关层正确填充
- [ ] `/scada/value/stream` 是否限制客户端 IP 白名单（防外网爬）
- [ ] Modbus/OPC UA/S7 端口是否仅对内网开放

## 七、收尾——这套项目的价值

写到这里，10 章连载就结束了。

回头看这套 `scada-collect`，它没有什么革命性的东西：协议驱动是 j2mod/Milo/PLC4X 三个开源库的组合、时序库是 TDengine、告警引擎是 ISA-18.2 简化版、推送是 SSE——每一个组件单拿出来都是工业 SCADA 圈子的标配。

但它的价值不在单点技术，在于**把这些组件按"中小制造工厂"的实际约束拼起来**：

- 不引入 ThingsBoard 那种插件式 SPI + Netty Pipeline 复杂度——二开团队维护不起
- 不引入 Redis/Kafka 多活依赖——客户现场没这预算
- 不追求 ISA-18.2 完整版的十几个状态——简化版覆盖 80% 场景就够
- 不把告警做成 DSL——单点告警的硬规则足够
- 不用 WebSocket——SSE 在 95% 推送场景下更优
- 不用 MyBatis-Plus 拦截器打 TDengine——独立 JDBC 包更直接

每一个"不做"背后都是一次明确的取舍。商用 SCADA 项目的真正难点，从来不是"能做什么"，而是"不做什么"——一个上得了生产、客户买得起、运维维护得动、二开团队改得动的 SCADA 系统，比一个功能全但维护不起的"大而全"系统值钱得多。

我从第一章的"为什么基于 yudao 二次开发"开始，到这一章的"商用上线与复盘"，10 章走下来，希望你能看到的是：商用工业软件的工程方法论——按业务约束选型、按业务场景取舍、按业务节奏调优、按业务边界收口。

这套代码已经推到 https://github.com/sunrise314/scada-collect ，欢迎 issue、欢迎 PR、欢迎在你的工厂里跑一跑。如果你也在做工业 SCADA 项目，希望这 10 章能帮你少踩几个坑。
